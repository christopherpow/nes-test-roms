The DMC channel enable/disable controls the DPCM memory fetch and not the playback unit itself. If a byte makes it into the sample buffer, it will always be played regardless of the state of the channel. The sample is considered done when the last byte is fetched into the sample buffer, even though there are still about 15 bits waiting to be played back. The exact timing here is not something I have tested thoroughly and would involve probably 2 tests: doing enable writes to $4015 at every cycle position in proximity to the end of sample playback, and finding the exact IRQ timing for when sample playback ends. I believe you've done the latter, but I'm not familiar with the data and I think no one has done the former.


This extra DMA sounds like the extra DMA bug I researched earlier in the thread, described here, tested by the implicit stop test, and documented on the wiki. Specifically, this issue appears to be present on post-1990 CPUs and not present on pre-1990 CPUs, so all H's and some G's have it.

There's another test I wrote that uses CPU test mode to further check the behavior of the extra DMA. I've attached a WIP version to this post; ideally I'll make this into a pass/fail test eventually. This test requires implementing $401A read, which returns the current DMC level. Mesen was able to pass the implicit and explicit stop tests without passing this test at first, though I don't remember what was causing Sour trouble. Mesen now has a test mode option that implements the readable test mode registers and passes this test. From right to left, the 8 columns in this test correspond to the first 8 rows of the implicit stop test, testing the DMC level after each bit is played to verify exactly what is played. The test showed that the extra byte was played and came from the same address as the first.
